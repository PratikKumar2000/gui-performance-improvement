  Test harness scripts (SyncRegression/):

        Folding, hierarchy order, cross-technology bucketing, malformed input,
        chunk balance; dry run only, does not mutate Atoll.
    PSTO_PARALLEL_SCALING_TEST.sql

        real writes at ver_nr=0 but measured as scaling, not functional stress.
    PSTO_PARALLEL_DELETE_TEST.sql
        Cross-chunk separation contention in Delete mode; snapshot/restore.
    PSTO_PARALLEL_CONCURRENT_TEST.sql
        Two overlapping runs: same ids, disjoint ids at shared sites, concurrent
        Delete; Update paths do not permanently mutate, Delete uses restore.
    PSTO_PARALLEL_TEST_SNAPSHOT.sql
        Snapshot and restore tooling shared by destructive tests.
    PSTO_PARALLEL_LOCK_MONITOR.sql
        Per-run diagnostics and wait-event reporting when V$ views are granted.

  Problem replaced

    Call sites previously looped PSTO_MASTER_BF once per object id. A bulk caller
    therefore paid N round trips (or N in-database calls in a PL/SQL loop) and
    could see only the last outcome: PSTO_MASTER_BF exposes a single V_RCODE /
    V_MESSAGE OUT pair, so id 3 of 8,000 failing and id 8,000 succeeding left the
    caller believing the whole batch succeeded. The wrapper stages every supplied
    id in PSTO_SYNC_WORK keyed by RUN_ID, runs work with optional parallelism,
    and returns aggregate OUT parameters while preserving one auditable row per
    SRC_OBJ_ID.

  Design rationale captured in API header (lines 1-136)

    The header documents measured scaling, CSV-path prohibition, transaction-semantics
    change, KDT partitioning for SITES check-then-act, ~3 s startup threshold math,
    three-phase chunk model, XB fold semantics, CR/LF skip policy, and per-id results
    query pattern. Those themes are woven through Parts 2-5 below rather than copied
    verbatim.

Headline conclusion

  Even at 20,000 objects and 7 concurrent sessions the speedup is only 1.37x, not
  7x. Measured serial cost is ~0.92-1.65 ms per 10-char LTE cell, not ~80 ms. At
  ~1 ms per object the run is dominated by a shared resource rather than CPU, so
  extra sessions mostly add contention rather than throughput.

  Parallelism only pays above roughly 3,000 objects (break-even ~2,858 at level 8
  with C_MS_PER_OBJ=1.2 and C_STARTUP_MS=3000). Below that threshold the wrapper
  correctly stays serial. This wrapper is worth deploying for bulk interfaces
  (imports, migrations, PSTO_DAILY_SYNC) and worth almost nothing for a single-
  object GUI save.

Fixed ~3 s slave startup (no-op PSTO_MASTER_BF, V_VER_NR=-1 short-circuit)

  Startup cost is independent of workload and chunk count until bucket count explodes
  task creation; the serial threshold exists so ordinary saves do not pay 3 s.

PART 7 — WHAT WAS FOUND AND FIXED ALONG THE WAY
-----------------------------------------------

C_MS_PER_OBJ recalibration (80 -> 1.2)

  The estimate 80 ms/object implied break-even ~50 objects at level 4. Measured
  serial cost from scaling test: 460 ms/500, 1860 ms/2000, 5910 ms/5000 -> ~1 ms
  each. Wrong constant actively routed mid-sized batches parallel, producing 0.15x
  at 500 objects and 0.54x at 2,000 before fix.

NTILE replaced by round-robin MOD(ROW_NUMBER()...)

  NTILE splits ordered keys into equal-sized groups, putting the N heaviest
  locations in bucket 1. Measured on 400 cells: buckets 7 to 113 rows. Round-
  robin on cnt DESC spreads load so workers finish together.

Unreachable deadlock retry fixed

  Worker had PRAGMA EXCEPTION_INIT(e_deadlock, -60) branch never firing because
  PSTO_MASTER_BF wraps all errors as ORA-20002. All 185 recorded failures carry
  rcode -20002, none -60. Message sniffing unreliable due to nested SUBSTR(SQLERRM,
  1, 200) truncation. Fix: unconditional one retry on any error; ATTEMPTS column
  exposes retries. Caveat unchanged: retry may re-run partial work — safe only
  because BFs use COUNT(1) existence checks before INSERT.

PSTO_MASTER_BF CSV batching path documented as unusable

  Lines 169/172 dispatch 10-char cells on V_NET_TYP from whole string (line 26) not
  V_NET_TY per token (line 153) — mixed LTE/5G batch misroutes. Lines 185/190
  duplicate ELSIF V_NET_TY IN ('RR') making PSTO_STOREPR_BF unreachable. Wrapper
  passes single ids only.

SESSION_ID added as fan-out evidence

  Overlapping timestamps insufficient at ~1 ms/object; USER_PARALLEL_EXECUTE_CHUNKS
  dropped after task completes. Worker stamps SYS_CONTEXT('USERENV','SID').


PART 8 — DEAD CODE AND CALIBRATION GAPS FOUND IN REVIEW
-------------------------------------------------------

(a) PSTO_SYNC_WORK.PARENT_OBJ_ID written, never read

  Written: staging INSERT lines 438-440 in PSTO_MASTER_PARALLEL_API.sql
           CASE WHEN c.skip_reason IS NULL AND c.obj_level IN (2,3)
                THEN FSTO_PSTO_PARENT_ID(P_VER_NR, c.obj_id)

  Not read in: PSTO_MASTER_PARALLEL_WRK, orchestrator summary, fold MERGE, or any
  harness query in this codebase.

  Leftover from ancestor-pruning in an earlier consolidated design (not present in
  current single API file): child whose ancestor was also Pending in same run was
  marked Pruned with PRUNED_BY set to ancestor id and re-queued if ancestor Failed.
  Current code: PRUNED_BY only set to obj_id for XB fold duplicates (lines 455-459).

  Column has no COMMENT ON COLUMN unlike siblings (09_create_parallel_sync_api.sql
  documents other columns at lines 209-217 but not PARENT_OBJ_ID).

  Bulk cost: for each 10-char cell (obj_level 3) FSTO_PSTO_PARENT_ID runs one
  SELECT against STOZELG/STOZELXG/STOZELL — one PL/SQL/SQL context switch and index
  lookup per row, serial on caller session inside staging INSERT before Step 3 COMMIT.
  For 17-char sectors (obj_level 2) function is pure CASE/SUBSTR — no SQL.

(b) Staging guard obj_level IN (2,3) never fires on Global Edit bulk path

  Verified in GlobalEditWorkerTask.java:
    findAlternativeIds (lines 448-505): cell-group branch SELECT s.ALT_ALT_ID (site
    alternative, 9 chars, obj_level 1); non-cell branch SELECT a.ALT_ID (9 chars).
    Alternative-tab path (lines 367-369): objectIdBuilder.append(alt.getId()) — also
    a BaseAlternative id (9 chars), never a 10-char cell or 17-char sector.

  Swing Global Edit does not send level 2 or 3 ids. Consistent with ~8,872 distinct
  alternatives for ~35,000 cells (~4 cells per alternative). Conclusion: per-row
  parent lookup never runs on GUI bulk path; it runs for callers passing sectors or
  cells (e.g. SYNC_FAILED_DAILY nightly backlog). Dropping column is tidiness, not
  GUI bottleneck removal.

(c) Calibration gap: C_MS_PER_OBJ=1.2 measured on 10-char LTE cells only

  GUI sends 9-char site alternatives; one site sync cascades through sectors and
  cells beneath it. Integration doc early overhead table: ~260 ms for one real 9-char
  site vs ~80 ms for one cell (pre-1.2-ms calibration era per-object table — the
  scaling measurement later showed ~1 ms/cell for bulk Update runs, a different
  measurement context).

  One global constant stands in for workloads differing by roughly two orders of
  magnitude in per-object cost. Currently fails safe for large site batches (sends
  them parallel when over threshold). Any future threshold tuning should depend on
  batch obj_level mix. No measurement of per-object cost for 9-char site batches
  through this wrapper exists yet — stated as gap to close, not measured fact.

PART 11 — BOTTOM LINE FOR LARGE BULK PROCESSING
-----------------------------------------------

This engagement's durable wins are not raw speed. Capped at 1.37x at 20,000 ids,
parallelism is a bulk-only tool above ~3,000 objects where ~3 s startup amortizes.

What actually bought value: per-id result channel in PSTO_SYNC_WORK (every SRC_OBJ_ID
auditable); correctness guards — KDT-key chunking preserving SITES invariant within a
run, three-phase ordering (global serial, parallel locations, MR/RR tail), per-object
COMMIT in workers, unconditional retry with ATTEMPTS visibility, INITRANS 16 on the
queue; calibrated refusal to parallelize sub-threshold batches after C_MS_PER_OBJ fix.

Raw parallel speedup is the least valuable deliverable because ~1 ms/cell work is
shared-resource bound — extra sessions add contention more than throughput.

For the GUI, the integration doc concluded that batching round trips was not worth
pursuing, on the assumption of ~80 ms per cell in its overhead table. The scaling
test later measured 0.92-1.65 ms per cell and C_MS_PER_OBJ was corrected from 80 to
1.2 — removing the basis for that conclusion. When server-side work per object is
around 1 ms, fixed per-call overhead stops being negligible in comparison and can
plausibly dominate. Round-trip removal is therefore worth measuring, and is now a
better candidate than adding sessions, given the 1.37x parallel ceiling at 20,000
ids. That is a hypothesis, not a result, for two separate reasons: no measurement of
per-call client-side overhead against this wrapper exists, and the recalibrated 1.2 ms
is cell-calibrated while the Global Edit path sends 9-character site alternatives
whose per-object cost is unmeasured and expected to be much higher because a site sync
cascades downward.

Next effort should close calibration by obj_level mix, consider removing dead
PARENT_OBJ_ID staging cost on cell/sector caller paths, apply INITRANS 16 in production
and measure ITL waits when V$ access exists, and retire single-id JDBC overload defects
documented in integration doc when switching callers to PSTO_MASTER_PARALLEL_BF_STR.
